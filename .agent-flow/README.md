# Процесс агентской разработки с сохранением контекста

Переносимый workflow для разработки с coding agent без потери ментальной модели
проекта. В корне репозитория требуется только `AGENTS.md`; конфигурация, планы,
решения и история задач остаются в `.agent-flow/`.

## Установка

Скопируй в корень существующего git-репозитория:

```text
AGENTS.md
.agent-flow/
```

Если в проекте уже есть `AGENTS.md`, объедини его проектные команды и конвенции
с разделами из комплекта, сохранив обязательную ссылку на `.agent-flow/`.

`AGENTS.md` пишется именно в верхнем регистре: это стандартное имя, которое
автоматически обнаруживает Codex и ряд других coding agents.

### PowerShell 5.1 или 7 в Windows

После распаковки выполни из корня проекта:

```powershell
Unblock-File .\.agent-flow\bin\flow.ps1
& .\.agent-flow\bin\flow.ps1 setup-local
& .\.agent-flow\bin\flow.ps1 validate
```

`Unblock-File` снимает метку загруженного из интернета файла. Если политика
выполнения всё равно запрещает запуск скриптов, разово используй:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\.agent-flow\bin\flow.ps1 setup-local
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\.agent-flow\bin\flow.ps1 validate
```

### Bash, zsh и другие POSIX-оболочки

После копирования выполни:

```bash
chmod +x .agent-flow/bin/flow
.agent-flow/bin/flow setup-local
.agent-flow/bin/flow validate
```

`setup-local` добавляет `/AGENTS.md` и `/.agent-flow/` в локальный
`.git/info/exclude`. Файл `.gitignore` проекта не меняется, а настройки flow не
появляются в `git status`, `git add .` и pull request данного клона.

Эту установочную команду выполняет человек. Агент не должен самостоятельно
изменять `.git/info/exclude`.

Если flow-файлы уже были добавлены в Git index, локальное исключение не удалит
их оттуда автоматически. Сначала проверь список, затем при необходимости оставь
файлы на диске и убери их только из index:

```bash
git ls-files -- AGENTS.md .agent-flow
git rm -r --cached -- AGENTS.md .agent-flow
```

Вторая команда меняет index. Перед её выполнением убедись, что эти пути
действительно не должны храниться в репозитории.

## Обновление существующей установки

Не удаляй каталог `.agent-flow/` целиком: в нём находятся локальная карта
проекта и история задач. Перед распаковкой новой версии сохрани и затем верни:

- `.agent-flow/PROJECT.md`;
- `.agent-flow/tasks/`;
- `.agent-flow/config.env`, если менял бюджеты.

Остальные файлы комплекта можно заменить файлами новой версии. Старый формат
`config.env` с конструкциями `${NAME:-value}` тоже читается обоими скриптами,
поэтому немедленная ручная миграция настроек не требуется.

## Первый запуск

Открой проект с агентом и отправь:

```text
Прочитай AGENTS.md и выполни .agent-flow/prompts/bootstrap.md.
Ничего не меняй в production-коде. Сначала покажи карту проекта и вопросы.
```

Агент исследует репозиторий, заполнит `PROJECT.md`, проверит реальные команды и
остановится для согласования. Исправь карту, если в ней потеряны доменные
инварианты или исторические причины решений.

## Новая фича или существенный bugfix

Вариант с готовым prompt:

```text
Следуй .agent-flow/prompts/new-feature.md.
Задача: <описание и ожидаемый результат>.
```

Или создай папку вручную.

PowerShell:

```powershell
& .\.agent-flow\bin\flow.ps1 new add-payment-retry
```

Bash:

```bash
.agent-flow/bin/flow new add-payment-retry
```

После этого агент пройдёт следующие gates:

1. Discovery без изменений production-кода.
2. Согласование решения и slice-плана.
3. Реализация одного небольшого slice.
4. Diff, evidence и твоё решение продолжать или исправлять.
5. Итоговые проверки и подготовка `final-review.md`.
6. Твоё финальное ревью и явное решение.
7. Короткая передача контекста; для `CRITICAL` — обязательный разбор
   диагностики и отката.

Отдельного AI-ревьювера в процессе нет: после каждого этапа и перед завершением
ревьювером являешься ты. Агент только организует diff, доказательства, риски и
порядок просмотра, затем ждёт твоего решения.

## Продолжение в новой сессии

Используй `.agent-flow/prompts/resume.md`. Источником истины считается task-папка,
а не память чата и не пересказ агента.

## Кто управляет Git

Только человек выполняет любые Git-операции, изменяющие состояние репозитория:
stage, commit, restore, reset, stash, branch, merge, rebase, fetch/pull/push и
удаление файлов через Git.

Агент использует Git только для чтения: `status`, `diff`, `log`, `show`,
`blame`, `ls-files`, `rev-parse` и другие информационные команды. Он:

- не делает `git add` и `git commit` после этапа;
- не откатывает файлы и не очищает working tree;
- не переключает ветки;
- считает staged-файлы и пользовательские commits нормальными;
- показывает полный diff от baseline задачи;
- при необходимости предлагает текст коммита, но не выполняет его.

## Полезные команды

| Действие | PowerShell | Bash |
| --- | --- | --- |
| Локально исключить flow-файлы | `& .\.agent-flow\bin\flow.ps1 setup-local` | `.agent-flow/bin/flow setup-local` |
| Создать task-папку | `& .\.agent-flow\bin\flow.ps1 new <slug>` | `.agent-flow/bin/flow new <slug>` |
| Показать состояния задач | `& .\.agent-flow\bin\flow.ps1 status` | `.agent-flow/bin/flow status` |
| Оценить незакоммиченный diff | `& .\.agent-flow\bin\flow.ps1 budget` | `.agent-flow/bin/flow budget` |
| Оценить результат от baseline | `& .\.agent-flow\bin\flow.ps1 budget <baseline-commit>` | `.agent-flow/bin/flow budget <baseline-commit>` |
| Оценить diff ветки от `main` | `& .\.agent-flow\bin\flow.ps1 budget main...HEAD` | `.agent-flow/bin/flow budget main...HEAD` |
| Проверить структуру | `& .\.agent-flow\bin\flow.ps1 validate` | `.agent-flow/bin/flow validate` |

Порог можно изменить в `.agent-flow/config.env`. Скрипт считает production,
tests, generated/lock и workflow-файлы отдельно; это ориентир, а не замена
инженерному суждению.

## Хранение task-документов

`PROJECT.md`, правила, task-документы и handoff остаются локально внутри
`.agent-flow/` и не коммитятся. Не клади в них секреты, персональные данные,
полные логи или крупные бинарные доказательства. Команды и существенные
результаты обычно достаточно зафиксировать текстом.

После закрытия задачи её папку можно оставить как компактную историю решений.
Если история становится слишком большой, сохрани `brief.md`, `plan.md`,
`final-review.md`, `handoff.md` и связанные decision records, а временные
заметки удали отдельным осознанным изменением.

Старые task-папки могут содержать `review.md`. Он считается устаревшим
артефактом и не используется как финальный вердикт. При продолжении такой
задачи агент создаёт `final-review.md`; новые задачи сразу создаются в новом
формате.

## Границы подхода

Workflow не гарантирует корректность и не заменяет CI, ревью кода или знание
домена. Он создаёт места, где агент обязан остановиться, а человек — принять
решение и восстановить понимание до того, как код станет частью системы.
