# Процесс агентской разработки с сохранением контекста

Этот репозиторий использует управляемую агентскую разработку. Цель — не
максимальная генерация кода, а изменения, которые человек успевает понять,
проверить и принять во владение.

## Обязательный контекст

Перед нетривиальной задачей прочитай:

1. `.agent-flow/PROJECT.md` — устройство и инварианты проекта.
2. `.agent-flow/POLICY.md` — границы автономности и бюджеты изменений.
3. `.agent-flow/WORKFLOW.md` — состояния задачи и human gates.
4. Файлы активной задачи в `.agent-flow/tasks/<task-id>/`, если она существует.

Для финализации дополнительно прочитай `.agent-flow/HUMAN_REVIEW.md` и
`.agent-flow/CONTEXT_HANDOFF.md`.

Если `PROJECT.md` ещё не инициализирован, сначала выполни
`.agent-flow/prompts/bootstrap.md`. До согласования карты проекта не меняй
production-код.

## Язык и назначение документов

- Все сообщения пользователю и все документы, предназначенные для чтения и
  согласования человеком, пиши на русском языке, если пользователь явно не
  попросил другой язык. К ним относятся `PROJECT.md`, файлы задачи (`brief.md`,
  `discovery.md`, `plan.md`, `progress.md`, `final-review.md`, `handoff.md`),
  записи решений и описание PR.
- Английский допустим только для имён файлов, команд, идентификаторов кода,
  названий библиотек, точных значений состояний и терминов без удобного русского
  аналога. Не переходи на английский язык в обычном тексте человекочитаемого
  документа.
- Внутренние инструкции агента, prompts и технические промежуточные данные,
  которые человек не должен читать или согласовывать, можно писать на наиболее
  токен-эффективном языке.
- `plan.md` предназначен прежде всего для согласования человеком и только затем
  для восстановления состояния агентом. Он должен быть понятен без чтения чата.
- Не копируй в `plan.md` всё содержимое `discovery.md`. Дай краткое выбранное
  решение и этапы реализации: не более 10 строк общего описания, не более 8
  пунктов на этап и ориентир до 120 строк на весь план.

## Локальные файлы flow и Git

- `AGENTS.md` и каталог `.agent-flow/` являются локальными настройками
  разработчика и не должны попадать в Git index, коммиты или pull request.
- Вся работа с состоянием Git принадлежит человеку. Никогда не выполняй команды,
  которые меняют index, commits, branches, refs или рабочее дерево через Git.
  В частности запрещены `git add`, `commit`, `restore`, `reset`, `checkout`,
  `switch`, `stash`, `clean`, `rm`, `mv`, `revert`, `merge`, `rebase`,
  `cherry-pick`, `fetch`, `pull`, `push`, создание/удаление веток и тегов.
- Разрешены только информационные Git-команды: `status`, `diff`, `log`, `show`,
  `blame`, `grep`, `ls-files`, `rev-parse`, `merge-base`, `diff-tree`,
  `branch --show-current`, `branch --list`, `tag --list`, `remote -v` и
  `check-ignore`.
- Не запускай `setup-local` самостоятельно: эта команда изменяет локальный
  `.git/info/exclude` и выполняется человеком при установке flow.
- Не добавляй эти пути в `.gitignore`. Для локального исключения человек один
  раз запускает подходящую для своей оболочки команду `setup-local`.
- Если flow-файлы уже отслеживаются Git, не удаляй их из index автоматически:
  сообщи человеку и покажи безопасную команду, оставив решение ему.
- Staged-файлы и новые commits, сделанные человеком во время задачи, являются
  нормальным рабочим процессом. Не называй их неожиданными только из-за их Git
  state и не проси очистить working tree.
- В начале задачи информационными командами зафиксируй baseline commit и снимок
  изменённых путей. В дальнейшем сообщай только о новых изменениях вне
  утверждённого scope или о реальном конфликте с редактируемыми файлами.
- Агент может предложить границу и текст коммита, но stage и commit выполняет
  только человек.

## Выбор скрипта flow

Перед запуском любой команды flow определи текущую оболочку:

- PowerShell: `& .\.agent-flow\bin\flow.ps1 <команда>`;
- Bash, zsh и другие POSIX-оболочки: `.agent-flow/bin/flow <команда>`.

Не предлагай пользователю Bash-команду, если он работает в PowerShell, и
наоборот. Упоминание `flow <команда>` в связанных документах означает запуск
одного из этих двух скриптов под текущую оболочку.

## Нерушимые правила

- Вся служебная информация агента хранится внутри `.agent-flow/`. Не создавай в
  корне `plan.md`, `todo.md`, отчёты, handoff-файлы и другие workflow-артефакты.
- Не начинай нетривиальную реализацию до явного согласования discovery и plan.
- Реализуй по одному independently reviewable slice. После каждого slice
  остановись и дождись решения человека. Наличие следующих пунктов плана не
  является разрешением продолжать.
- Бюджет slice по умолчанию — не более 300 изменённых строк production-кода и
  не более 5 production-файлов. Тесты и generated-файлы показывай отдельно;
  они не должны скрывать сложность изменения.
- Не добавляй без отдельного согласования: production dependencies, миграции,
  публичные API, новые сервисы/абстракции, изменения auth/security, форматов
  данных, протоколов, транзакционных границ или deployment topology.
- Если реальный scope, риск или архитектура отличаются от утверждённого плана,
  остановись, обнови task-документы и запроси новое решение.
- Предлагай человеку одну смысловую причину на коммит. Не смешивай в одном этапе
  feature, рефакторинг, форматирование и dependency updates.
- Не объявляй задачу готовой только по зелёному CI. Приведи воспроизводимые
  evidence: команды, результаты, manual/smoke scenario и ограничения проверки.
- Не скрывай неизвестность. Непроверенные выводы помечай как предположения.

## Классификация задачи

Полный task-flow обязателен, если изменение затрагивает несколько модулей,
меняет наблюдаемое поведение, содержит бизнес-логику или имеет средний/высокий
риск.

Упрощённый режим допустим только когда одновременно выполняются условия:

- ожидается не более 50 изменённых строк production-кода;
- меняется одна локальная область;
- нет изменения внешнего поведения, схемы, зависимости, security или
  архитектурной границы;
- проверка быстрая и однозначная.

Даже в упрощённом режиме сначала кратко сформулируй цель и `done when`, затем
покажи diff и результаты проверок.

## Запуск задачи

Для нетривиальной работы создай task-папку подходящей командой:

```powershell
& .\.agent-flow\bin\flow.ps1 new <short-slug>
```

```bash
.agent-flow/bin/flow new <short-slug>
```

Заполняй документы по мере продвижения; не выдумывай факты заранее. Текущее
состояние должно быть видно в `brief.md` и `progress.md`.

## Критерии готовности

Изменение готово к merge, только если:

- acceptance criteria выполнены;
- утверждённый план либо выполнен, либо отклонения явно согласованы;
- релевантные тесты, lint, type checks, build и quality/security gates прошли;
- выполнен ручной или воспроизводимый smoke-сценарий, если это применимо;
- каждый этап просмотрен и принят человеком;
- агент подготовил `final-review.md`, а человек явно принял итоговый результат;
- `handoff.md` объясняет flow, инварианты, failure modes, observability и
  rollback;
- передача контекста завершена по `.agent-flow/CONTEXT_HANDOFF.md`; для режима
  `CRITICAL` проведён разбор диагностики и отката;
- `progress.md` имеет состояние `DONE`.
